# 12. ログ運用とビルド影響

`Runtime` / `Core` の `Debug.Log*` 呼び出しを、`#if UNITY_EDITOR` の内外で分類した。
`SymphonyDebugLogger` に `[Conditional("UNITY_EDITOR")]` 付きAPIが揃っているため、
**素の `Debug.Log` はビルドへ残る**という明快な基準で判断できる。

## 調査サマリ

| 分類 | 件数 |
| --- | --- |
| `#if UNITY_EDITOR` の内側（ビルドへ残らない） | 8 |
| `#if UNITY_EDITOR` の外側（ビルドへ残る） | 19 |
| └ うち誤用を伝える `LogWarning` / `LogError`（正当） | 12 |
| └ うち `SymphonyDebugLogger` 自身の実装（正当） | 3 |
| └ **うち情報ログで、利用側に出す必要が無いもの** | **4** |

全19件は[付録A](#付録a-ビルドへ残る-debuglog全19件)を参照。

## 【確定】公開ユーティリティが呼び出しごとに情報ログを出す

**場所**: [SymphonyAwaitable.cs:42](../../Assets/SymphonyFrameWork/Runtime/Utility/SymphonyAwaitable.cs)、
[SymphonyAwaitable.cs:71](../../Assets/SymphonyFrameWork/Runtime/Utility/SymphonyAwaitable.cs)

```csharp
public static async Awaitable BackGroundThreadActionAsync(Action action)
{
    // ...
    try { action.Invoke(); }
    finally { await Awaitable.MainThreadAsync(); }

    Debug.Log($"{action.Method} is done");   // ← 無条件・毎回
}
```

`SymphonyAwaitable` は公開ユーティリティであり、**利用側がバックグラウンド処理を呼ぶたびに
情報ログが1行出る**。しかも `action.Method`（`MethodInfo`）の `ToString()` を伴う文字列補間なので、
ログレベルの設定に関係なく**文字列が必ず構築される**。

`Application.SetStackTraceLogType` でスタックトレースを切っても、ログ自体は消えない。
利用側から抑止する手段が無い。

**同じファイルの他のAPI（`WhenAll`、`Completed`、`AwaitBridgeAsync` など約40のメソッド）は
一切ログを出していない。この2箇所だけが例外である。** デバッグ中の書き残しと見られる。

**修正方針**: 削除する。残す場合は `SymphonyDebugLogger.LogDirectForEditor` へ置換する
（同メソッドは `[Conditional("UNITY_EDITOR")]` が付いており、ビルドでは呼び出しごと消える）。

```csharp
SymphonyDebugLogger.LogDirectForEditor($"{action.Method} is done");
```

## 【確定】セーブのたびにデータ本体をログへ書き出す

**場所**: [SaveDataLoaderStrategy.cs:82](../../Assets/SymphonyFrameWork/Runtime/System/SaveSystem/SaveDataLoaderStrategy.cs)

```csharp
Debug.Log($"[{GetType().Name}]\nデータをセーブしました。 date : {data.SaveDate}\n{data}");
```

`{data}` は `SaveDataContent` の `ToString()` である。**セーブ1回につき、セーブデータの内容全体が
利用側のコンソールとログファイルへ出力される。**

オートセーブを実装した利用側では、これがセーブ周期ごとに発生する。加えて次の問題がある。

- **セーブデータの内容がプレイヤーのログファイルへ書き出される。** 内容によっては
  意図しない情報が出力先へ残る
- 文字列補間なので、`ToString()` の実行と文字列構築のコストが毎回発生する

[同ファイル:40](../../Assets/SymphonyFrameWork/Runtime/System/SaveSystem/SaveDataLoaderStrategy.cs)
の「データが見つからないので生成しました」も同様に情報ログで、初回起動時に登録セーブデータ型の数だけ出る。

**修正方針**: どちらも `SymphonyDebugLogger.LogDirectForEditor` へ置換する。
異常系である[同ファイル:52](../../Assets/SymphonyFrameWork/Runtime/System/SaveSystem/SaveDataLoaderStrategy.cs)
の `LogWarning`（復元失敗）は、利用側が知るべき情報なので**そのまま残す**。

## 【設計指摘】ログの出し分け基準がファイルごとに揃っていない

同じ「フレームワーク内部の情報ログ」に対して、3つの流儀が併存している。

| 流儀 | 例 | ビルドへ | 利用側から抑止 |
| --- | --- | --- | --- |
| `#if UNITY_EDITOR` + 設定フラグ | [ServiceLocator.cs:131-135](../../Assets/SymphonyFrameWork/Runtime/System/ServiceLocator/ServiceLocator.cs) | 残らない | Project Settings から可能 |
| `[Conditional("UNITY_EDITOR")]` 付きAPI | `SymphonyDebugLogger.LogDirectForEditor` | 残らない | – |
| 素の `Debug.Log` | [SymphonyAwaitable.cs:42](../../Assets/SymphonyFrameWork/Runtime/Utility/SymphonyAwaitable.cs) | **残る** | 不可 |

**`ServiceLocator` の書き方が最も良い。**

```csharp
#if UNITY_EDITOR
    if (ServiceLocateLogOption.IsDestroyInstanceLogEnabled)
    {
        Debug.Log($"{type.Name}が登録解除されました。");
    }
#endif
```

ビルドから消えるうえ、Editorでも Project Settings から個別に切れる。
`SaveSystem` / `SceneLoader` / `Audio` には同等の出し分けが無い。

**修正方針**: **`Documentation/CodeGuidelines.md` の「エラー処理とログ」節へ、
重要度別にどのAPIを使うかの対応表を追加した。** 修正時はこれを基準にする。

| 重要度 | 使うもの | ビルドへ |
| --- | --- | --- |
| 利用側の誤用・異常系を伝える | 素の `Debug.LogWarning` / `LogError` | **残す** |
| フレームワーク内部の動作追跡 | `#if UNITY_EDITOR` + 設定フラグ | 残さない |
| 一時的なデバッグ | `SymphonyDebugLogger.LogDirectForEditor` | 残さない |

条文追加前は「ログは `SymphonyDebugLogger` を使う」に留まっており、
**素の `Debug.Log` を使ってよい場面の線引きが無かった**。
本観点の指摘4件は、いずれもその線引きの不在から生じている。

## 検証したが問題が無かった項目

- **`ServiceLocator` の情報ログ5件はすべて `#if UNITY_EDITOR` で正しく囲まれている。**
  ビルドへ残るのは「登録されていません」という誤用警告2件のみで、これは残すべきもの
- **`UnitySceneLoader.cs:74,100` の `LogError` は、直後に `return` している。**
  エラー検知後に処理を継続している箇所は0件だった
- **`SymphonyDebugLogger.cs:40-42` の `Debug.Log` はロガー自身の実装。**
  `LogDirect` は意図的に `[Conditional]` を持たない設計（ビルドでも出力する公開API）
