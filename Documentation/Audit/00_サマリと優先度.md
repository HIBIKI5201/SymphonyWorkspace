## 本監査の読み方

観点ごとに個別ファイルへ分割している。すべての指摘には `file:line` を付し、**確度**を明示している。

| 表記 | 意味 |
| --- | --- |
| **確定** | コードを直接読んで動作上の問題が確認できたもの |
| **要検証** | 静的に強く疑われるが、実行時の呼び出し経路次第で影響が変わるもの |
| **設計指摘** | 動作は正しいが、一貫性・保守性・拡張性の観点で改善余地があるもの |

**ツールの出力そのものは指摘ではない。** 機械走査143件・Project Auditor 1,268件のうち、
読解を通して指摘として残したのは下表のとおりである。差の大半は誤検出と、
`GetHashCode` の慣用素数のような「検出はされるが意味を持たない」ものだった。

**監査中に走査スクリプト自体も直している。** 誤検出が判明した3つの検査を修正し、
誤検出率100%だった1つを削除、代わりに機械化の価値が高い2つを追加した。
経緯は[監査中に行った走査スクリプトの修正](#監査中に行った走査スクリプトの修正)に記載する。

### 費用対効果が最も高い3件

上表のうち、**修正が数行で済むのに影響が広い**もの。

1. **`SymphonyAwaitable.cs:42,71` の `Debug.Log` を削除するか `SymphonyDebugLogger.LogDirectForEditor` へ置換する**（2行）— 利用側のビルドサイズとコンソールノイズが同時に消える。同じファイルの他のAPIはログを出していないので、この2箇所だけが例外である。
2. **`SymphonyHUDDrawer.GetMemoryUsageString` の補間を `ToString()` 呼び出しへ変える**（4行）— 同ファイルの [line 87](../../Assets/SymphonyFrameWork/Runtime/Debug/DebugHUD/Internal/SymphonyHUDDrawer.cs) が既に `fps.ToString("0.")` と書いており、**正しい書き方が同じメソッドの11行上にある**。揃えるだけで毎フレームのボックス化が消える。
3. **`grace = 120` を `SymphonyConstant` へ集約する**（3箇所 × 1行）— 同じ既定値が [SymphonyLocateObject.cs:48](../../Assets/SymphonyFrameWork/Runtime/Component/SymphonyLocateObject.cs)・[ServiceLocator.cs:345](../../Assets/SymphonyFrameWork/Runtime/System/ServiceLocator/ServiceLocator.cs)・[ServiceLocator.cs:405](../../Assets/SymphonyFrameWork/Runtime/System/ServiceLocator/ServiceLocator.cs) に重複しており、片方だけ変えると挙動が食い違う。

## 全体所感

**コードベースの質は非常に高い。** 特に以下は明確な強みで、監査中に「問題が無いことを確認して終わった」観点が10ある。

- **公開メンバー327件すべてにXMLドキュメントが付いている。** 記載漏れゼロ
- **`[Obsolete]` 11件すべてが `Deprecations.md` に記載済み。** `AGENTS.md` §0.1 の規約が実際に守られている
- **`Time.timeScale` / `QualitySettings` / `targetFrameRate` への書き込みが0件。** 利用側のグローバル状態を汚さない
- **`.cs` 155ファイルすべてがUTF-8 BOM付き。** `TODO` / `FIXME` が0件、3段以上のメンバーチェーンが0件
- **`Internal/` 配下49ファイルに `public` 型の漏れが無い**
- **static 状態の解放が徹底している。** 下記はいずれも正しい実装で、**修正時のテンプレートとして使える**
  - [SymphonyDebugLogFileWriter.cs:43-44](../../Assets/SymphonyFrameWork/Editor/Debug/SymphonyDebugLogFileWriter.cs) — `-=` してから `+=` する冪等購読。Domain Reload 無効下での二重購読を構造的に防いでいる
  - [ServiceLocateRegistry.cs:99](../../Assets/SymphonyFrameWork/Runtime/System/ServiceLocator/Internal/Application/ServiceLocateRegistry.cs) — `Action remaining = existing - action;` で辞書内デリゲートを安全に解除
  - [AutoEnumGenerator.cs:98-103](../../Assets/SymphonyFrameWork/Editor/Generator/EnumGenerate/AutoEnumGenerator.cs) — `Shutdown()` が `Dispose()` で一括解除
  - [PackageInitializer.cs:38](../../Assets/SymphonyFrameWork/Editor/PackageInitializer.cs) — 注入した static デリゲートを `null` へ戻す
- **`ServiceLocator` の情報ログが `#if UNITY_EDITOR` で正しく囲まれている**（[128行以降](../../Assets/SymphonyFrameWork/Runtime/System/ServiceLocator/ServiceLocator.cs)）。ビルドへ残るのは誤用を伝える警告のみ

したがって本監査の指摘は「破綻の修復」ではなく「**既に高い水準をさらに揃える**」性質のものが中心である。
**唯一の例外が最優先1件目のサンプル出荷問題**で、これは水準の揃えではなく構成の誤りにあたる。

指摘の多くは「同じ問題に対して正しい実装が既にコードベース内にある」形を取っている。
上記のテンプレートを横展開するだけで解消できるものがほとんどである。

## 監査中に行った走査スクリプトの修正

**走査の誤検出は、読解で潰すだけでなく `scripts/audit_scan.py` へ反映した。**
同じ誤検出を次回も読み直すことになるためである。

| 検査 | 変更 | 効果 |
| --- | --- | --- |
| `01_subscribe_imbalance` | 算術の `+=`（`timer += Time.deltaTime`）を右辺の形で除外 | 9件 → 5件 |
| `12_raw_debug_log` | `#if UNITY_EDITOR` の内外を追跡し、ビルドへ残るものだけを指摘へ | 27件 → 19件（+ 参考8件） |
| `B_obsolete_undocumented` | 複数行属性とジェネリックに対応し、`nameof` の誤検出を解消 | 誤検出7件 → 0件 |
| `B_editor_module_undocumented` | **削除。** ディレクトリ名一致では誤検出率100%（→ [B3](B3_Editor機能とドキュメント同期.md)） | 誤検出2件 → 0件 |
| `B_deprecation_stale` | **追加。** `Deprecations.md` → コードの逆方向検査（→ [B2](B2_Obsoleteとドキュメント同期.md)） | 移し忘れを検出可能に |
| `B_line_ending` | **追加。** `git ls-files --eol` によるindex側の改行検査（→ [B8](B8_文字コードとmeta.md)） | 204ファイルを検査 |

**削除した検査と追加した検査の違いは「手掛かりがどこにあるか」である。**
Editor機能とドキュメントの対応は**読めば分かる**が表現が一意でないため機械化に向かない。
一方、削除済みシンボルの移し忘れと改行コードは**読んでも分からない**
（コードに痕跡が無い / ワーキングツリーが変換済み）ため、機械化の価値が高い。
