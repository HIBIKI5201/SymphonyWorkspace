# 11. 非同期処理の不純点

`async void` と、`CancellationToken` を引数に持たない非同期メソッドを機械的に列挙し、
`Documentation/CodeGuidelines.md` の「非同期処理」節および
`Documentation/DesignPhilosophy.md` の「非同期処理の型」節と照合した。

## 調査サマリ

| 分類 | 件数 |
| --- | --- |
| `async void` | 4（Runtime 1 / Editor 3） |
| `CancellationToken` 引数を持たない非同期メソッド | 16 |
| `CancellationToken` の登場箇所 | 98 |
| 非同期メソッド総数（`Awaitable` / `Task` / `ValueTask`） | 52 |

`Task` から `Awaitable` への移行は既に進んでおり、
`Documentation/Designs/AwaitableMigration.md` に方針が残っている。

## 【確定】`async void` の公開APIが、宣言した例外を呼び出し元へ届けられない

**場所**: [SymphonyAwaitable.cs:17-43](../../Assets/SymphonyFrameWork/Runtime/Utility/SymphonyAwaitable.cs)

```csharp
/// <exception cref="ArgumentNullException">
///     <paramref name="action"/>がnullの場合に送出する。
/// </exception>
public static async void BackGroundThreadAction(Action action)
{
    if (action == null)
    {
        throw new ArgumentNullException(nameof(action));   // ← 呼び出し元へ届かない
    }

    await Awaitable.BackgroundThreadAsync();

    try { action.Invoke(); }
    finally { await Awaitable.MainThreadAsync(); }
}
```

`async void` メソッドでは、**最初の `await` より前で発生した例外も含め、本体全体が
コンパイラ生成のステートマシンの try/catch に包まれる**。捕捉された例外は
呼び出し元へ再送出されるのではなく、`SynchronizationContext` へポストされて
未処理例外になる。

つまり利用側が次のように書いても捕捉できない。

```csharp
try
{
    SymphonyAwaitable.BackGroundThreadAction(null);
}
catch (ArgumentNullException)
{
    // ここへは来ない。例外は未処理例外としてコンソールへ出る
}
```

**XMLドキュメントの `<exception>` は、`async void` では契約として成立しない。**
同じ問題が `action.Invoke()` 内で発生した例外にも当てはまり、
`try`/`finally` に `catch` が無いため利用側は失敗を知る手段が無い。

### 修正方針

**すぐ下に正しい実装がある。** [同ファイル:53](../../Assets/SymphonyFrameWork/Runtime/Utility/SymphonyAwaitable.cs)
の `BackGroundThreadActionAsync` は本体が同一で、戻り値だけが `Awaitable` になっている。
こちらは例外が正しく awaiter へ伝播する。

したがって `BackGroundThreadAction` は次のいずれか。

1. **`[Obsolete]` を付けて `BackGroundThreadActionAsync` へ誘導し、次のメジャーで削除する**（推奨）
2. 残すなら **XMLドキュメントから `<exception>` を削除し、
   「例外は呼び出し元へ伝播せず未処理例外になる」と明記する**

1を選ぶ場合は `Documentation~/Deprecations.md` へ行を追加すること（`AGENTS.md` §0.1）。

残り2件にも同じコメントを付けることを提案する。

## 【要検証】`WhenAll` が `CancellationToken` を受け取らない

**場所**: [SymphonyAwaitable.cs:113](../../Assets/SymphonyFrameWork/Runtime/Utility/SymphonyAwaitable.cs)

`SymphonyAwaitable` の公開APIの多くは `CancellationToken token = default` を持つが、
`WhenAll` と `BackGroundThreadActionAsync` は持たない。

`WhenAll` は渡された各 `Awaitable` が自前のトークンを持っている前提であれば成立するが、
**「全体をまとめて中断する」手段が無い**。シーン破棄時に一括で止めたい利用側は、
各 `Awaitable` の生成時点までさかのぼってトークンを配る必要がある。

クラスのXMLドキュメント（[同ファイル:10-14](../../Assets/SymphonyFrameWork/Runtime/Utility/SymphonyAwaitable.cs)）には
`WhenAny` を提供しない理由が明記されているが、`WhenAll` のトークン非対応については記載が無い。

**修正方針**: 意図的なら理由をXMLドキュメントへ記載する。意図的でないなら
`WhenAll(CancellationToken token, params Awaitable[] awaitables)` のオーバーロードを追加する。
**既存シグネチャを変えると破壊的変更になる**ため、追加で対応する。

## 【設計指摘】`CancellationToken` 非対応16件の内訳

16件のうち、公開APIは2件のみで、残り14件は `private` / `internal` の内部メソッドである。
内部メソッドは呼び出し元がトークンを保持していれば問題にならないため、
**一律の指摘にはしない**。全件は[付録A](#付録a-cancellationtoken-引数を持たない非同期メソッド全16件)を参照。

注目すべきは [IInitializeAsync.cs:20](../../Assets/SymphonyFrameWork/Runtime/Interface/IInitializeAsync.cs) の
`DoInitialize(...)` で、**これは利用側が実装するインターフェースである**。
トークンを引数に持たないため、利用側の初期化処理は中断手段を持てない。
`IGameObject.destroyCancellationToken` を併用する前提であれば、その旨をXMLドキュメントへ書くべきである。
