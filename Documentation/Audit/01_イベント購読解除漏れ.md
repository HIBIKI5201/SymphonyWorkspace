# 01. イベント購読解除漏れ

`+=` と `-=` をファイル単位で機械的に突き合わせ、差分のあるファイルを個別に精査した。
算術の `+=`（`timer += Time.deltaTime` など）は右辺の形で除外している。

## 調査サマリ

| 分類 | ファイル数 |
| --- | --- |
| 購読(`+=`)があり解除(`-=`)が一切ない | 3 |
| `+=` が `-=` より多い（部分的解除漏れ） | 2 |
| **読解の結果、実際に解除漏れだったもの** | **0** |
| `static event` の総数 | 7 |

**5件すべてが誤検出だった。** ただし1件について、解除APIの非対称という設計上の指摘がある。

---

## 【要検証】ロード完了callbackに個別解除の手段が無い

**場所**: [SceneLoadRegistry.cs:217-232](../../Assets/SymphonyFrameWork/Runtime/System/SceneLoader/Internal/Application/SceneLoadRegistry.cs)

```csharp
internal bool RegisterLoadedAction(string sceneName, Action action)
{
    // ...
    if (!_loadedActions.TryAdd(sceneName, action))
    {
        _loadedActions[sceneName] += action;
    }
    return false;
}
```

解除経路は `TakeLoadedAction`（[同ファイル:236-245](../../Assets/SymphonyFrameWork/Runtime/System/SceneLoader/Internal/Application/SceneLoadRegistry.cs)）
だけで、これは**そのシーンの全callbackをまとめて取り出して削除する**。
個別のcallbackだけを取り消す手段が無い。

したがって、**登録したシーンが結局ロードされなかった場合、そのデリゲートは
`Clear()`（[同ファイル:251](../../Assets/SymphonyFrameWork/Runtime/System/SceneLoader/Internal/Application/SceneLoadRegistry.cs)）
まで保持され続ける**。デリゲートは登録側のインスタンスを捕捉しているため、
その間は解放されない。

### なぜ「要検証」か

`Clear()` が `ResetRuntimeState` 経路で呼ばれていれば、Play Mode 単位では確実に解放される。
実害が出るのは「1回のPlay Mode中に、ロードされないシーンへ大量のcallbackを登録し続ける」
使い方をした場合に限られる。**利用側の使い方次第で影響が変わる。**

### 対になる実装が同じフレームワーク内にある

**`ServiceLocateRegistry` は同じ「辞書に貯めたデリゲート」を扱っているが、個別解除APIを持つ。**

```csharp
// ServiceLocateRegistry.cs:88-107
internal void UnregisterWaitingAction<T>(Action action)
{
    Type serviceType = typeof(T);
    if (!_waitingActions.TryGetValue(serviceType, out Action existing)) { return; }

    Action remaining = existing - action;     // ← 辞書内デリゲートの安全な解除
    if (remaining == null)
    {
        _waitingActions.Remove(serviceType);
        return;
    }
    _waitingActions[serviceType] = remaining;
}
```

**この実装は模範的である。** 辞書の値に対して `-=` を直接書くと、結果が `null` になったときに
空エントリが残る。ローカルへ取り出して減算し、`null` なら `Remove` する形はその問題を回避している。

**修正方針**: `SceneLoadRegistry` へ `UnregisterLoadedAction(string sceneName, Action action)` を
追加し、`ServiceLocateRegistry.UnregisterWaitingAction` と同じ形で実装する。
どちらも `internal` なので**破壊的変更にはならない**。

## 【設計指摘】UITKウィンドウのラムダ購読8件

**場所**: [AutoEnumGeneratorWindow.cs:28,34,40](../../Assets/SymphonyFrameWork/Editor/Administrator/UITK/CS/AutoEnumGeneratorWindow.cs)、
[PauseWindow.cs:54,55](../../Assets/SymphonyFrameWork/Editor/Administrator/UITK/CS/PauseWindow.cs)、
[SaveDataWindow.cs:92,93,94](../../Assets/SymphonyFrameWork/Editor/Administrator/UITK/CS/SaveDataWindow.cs)

```csharp
sceneList.button.clicked += () => AutoEnumGenerator.SceneListEnumGenerate();
_pauseButton.clicked += () => SetPause(true);
```

匿名ラムダは参照を保持しないため `-=` が書けない。ただし購読先の `Button` は
`EditorWindow` のルート `VisualElement` に属し、**ウィンドウが閉じられれば
`VisualElement` ごと破棄される**。デリゲートはウィンドウより長生きしない。

**したがって実害は無い。** UI Toolkit の慣用的な書き方でもある。

指摘として残したのは、**次回以降の監査で毎回この8件を再検討しなくて済むようにするため**である。

**`Documentation/CodeGuidelines.md` の「Editor拡張」節へ条文を追加した。**
既存の「解除できない匿名callbackを登録しない」との関係を、
**購読先の寿命で判断する**と整理してある。

| 購読先 | ラムダ購読 |
| --- | --- |
| Windowが所有する `VisualElement` | **可**（Windowと同時に破棄される） |
| `EditorApplication.update` / static event / Runtime側のReactiveProperty | 不可（Windowより長生きする） |

この8件はいずれも前者にあたる。**次回監査では条文を根拠に「該当なし」と判定してよい。**

## 検証したが問題が無かった項目

### `static event` 7件はすべて正しく解除されている

| 場所 | 解除経路 | 判定 |
| --- | --- | --- |
| [SymphonyDebugLogger.cs:52](../../Assets/SymphonyFrameWork/Runtime/Debug/SymphonyDebugLogger.cs) `OnLogDirect` | [SymphonyDebugLogFileWriter.cs:43,57](../../Assets/SymphonyFrameWork/Editor/Debug/SymphonyDebugLogFileWriter.cs) | **模範的** |
| [PauseManager.cs:36](../../Assets/SymphonyFrameWork/Runtime/System/Pause/PauseManager.cs) `OnPauseChanged` | `ResetRuntimeState` | 正当 |
| [SaveStore.cs:158](../../Assets/SymphonyFrameWork/Runtime/System/SaveSystem/SaveStore.cs) `OnCurrentViewModelChanged` | `ResetRuntimeState` | 正当 |
| `OnHostChangesPending` ×3（Editor） | Editorセッション同一 | 正当 |

**`SymphonyDebugLogFileWriter` の書き方が最も良い。**

```csharp
// line 43-44
SymphonyDebugLogger.OnLogDirect -= EnqueueLog;   // 先に解除
SymphonyDebugLogger.OnLogDirect += EnqueueLog;   // それから購読
```

**Domain Reload が無効なため、`+=` だけを書くと再初期化のたびに購読が積み上がる。**
解除してから購読する冪等な形は、その事故を構造的に防いでいる。この2行はテンプレートとして
横展開する価値がある。

### `AutoEnumGenerator` は `Dispose()` で一括解除している

[AutoEnumGenerator.cs:81-104](../../Assets/SymphonyFrameWork/Editor/Generator/EnumGenerate/AutoEnumGenerator.cs)
は `+=` が3件で `-=` が0件だが、`Initialize()` は購読の**直前**に `Dispose()` を呼び、
`Shutdown()` は3つすべてを `Dispose()` している。

```csharp
public void Dispose() => OnSettingChanged = null;   // TagsAndLayersPostProcessor.cs:67
```

`-=` を使わずイベント自体を `null` にする形で、上と同じ冪等性を得ている。**問題無し。**

### `SymphonyVisualElement.EditorAssetLoader` は `null` へ戻されている

[PackageInitializer.cs:27,38](../../Assets/SymphonyFrameWork/Editor/PackageInitializer.cs) が
設定と解除の両方を行っている。static デリゲートがEditorのコードを掴んだままにならない。
