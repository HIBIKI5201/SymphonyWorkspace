# B4. 利用側への非侵襲性

**指摘なし。**

フレームワークが利用側プロジェクトのグローバル状態・設定・シーンを
勝手に書き換えていないかを確認した。`Documentation/DesignPhilosophy.md` の
「利用側への非侵襲性」節が正本である。

## 調査サマリ

| 項目 | 件数 |

---

## `Time.timeScale` を触らない `PauseManager`

特筆すべきは **`PauseManager` が `Time.timeScale` を一切変更していない**ことである。

ポーズ機能の実装として `Time.timeScale = 0` は最も安直な手段だが、
これを行うと次の副作用が利用側へ及ぶ。

- 利用側が独自にスローモーション演出を実装している場合に衝突する
- `Time.deltaTime` に依存する全処理が停止し、UIアニメーションまで止まる
- ポーズ解除時に元の `timeScale` を復元する責務が発生する

`PauseManager` は代わりに `IPausable` インターフェースと
`PauseManager.Pause` フラグによる**協調的なポーズ**を採っている。

```csharp
// SymphonyTween.cs:78-84 — ポーズ中はタイマーを進めない
if (PauseManager.Pause)
{
    timer += Time.deltaTime;
    await Awaitable.NextFrameAsync(token);
    continue;
}
```

**利用側が何も対応しなければ何も止まらない**ため、非侵襲性が保たれている。

## `[RuntimeInitializeOnLoadMethod]` の副作用

`SymphonyOrchestrator` が起動時にシステムGameObjectを1つ生成する。
これは利用側から見て観測可能な副作用だが、次の理由で妥当と判断する。

- **フレームワークの機能を使うために必要な最小限のもの**である
- 生成されるオブジェクトは1つで、`Internal/` 配下の型のみを持つ
- `Documentation~/` に説明がある

## `Resources/` へのアセット生成

`SymphonyConfigManager.AllConfigCheck()` が `[InitializeOnLoad]` で
`Assets/Resources/SymphonyFrameWork/` へ設定アセットを生成する。

**これは Editor でのみ動作し、Player ビルドでは起きない。** 生成物の型は
`internal` で、利用側のコードから参照できない（→ [B5](B5_自動生成物との境界.md)）。

`Resources/` フォルダへ書き込むこと自体は利用側のプロジェクト構造へ介入するが、
**設定アセットの置き場としては標準的な選択**であり、
`Project Settings > SymphonyFrameWork` から場所が確認できる。

## 確認できていないこと

**Player ビルドでの実挙動は検証していない。**
`#if UNITY_EDITOR` の外側にあるコードが、利用側のランタイムへ
どの程度の副作用を及ぼすかは、実際にビルドしないと分からない。

現時点で分かっている出荷時の副作用は次の2つで、
いずれも[12](12_ログ運用とビルド影響.md)で指摘済みである。

- `SymphonyAwaitable` の呼び出しごとの `Debug.Log`
- `SaveDataLoaderStrategy` のセーブごとの `Debug.Log`

**ログ出力も利用側のコンソールを汚す侵襲である。**
本観点の指摘としては[12](12_ログ運用とビルド影響.md)へ集約している。
