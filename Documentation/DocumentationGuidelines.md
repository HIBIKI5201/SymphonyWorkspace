# Symphony Framework ドキュメントガイドライン

このドキュメントは、Symphony Framework とワークスペースの **Markdown文書をどう書くか** の共通ルールです。[CodeGuidelines.md](./CodeGuidelines.md) がコードの書き方であるのに対し、こちらは文書の書き方に限定しています。

どの変更で、どの文書を更新するかの対応表は [CONTRIBUTING.md `## 6. 変更に応じて同時に更新するもの`](./CONTRIBUTING.md#6-変更に応じて同時に更新するもの) にあります。本ドキュメントは「更新すると決めた文書を、どう書くか」を扱います。

## 1. 文書の種別と役割

**文書ごとに読み手と役割が違います。役割を跨いだ内容を書き写さないでください。**

| 文書 | 読み手 | 役割 |
| --- | --- | --- |
| `README.md`（パッケージ） | 利用者（人間） | 何ができるかと、始め方。最初の1画面で価値が伝わること |
| `Documentation~/Modules/<モジュール>.md` | 利用者（人間・AI） | 1モジュールの正本。使い方、注意、Editor機能、内部構造 |
| `Documentation~/Architecture.md`、`EditorTools.md`、`Deprecations.md` | 利用者（人間・AI） | 単一モジュールに閉じない索引と横断情報 |
| `AGENTS.md`（パッケージ） | AIエージェント | 利用側コードを書くときの**行動契約**。導線と常時ルールだけ |
| `AGENTS.md`（ワークスペース） | AIエージェント | ワークスペースの構成、環境、自動生成物の区別 |
| `Documentation/`（ワークスペース） | 本体開発者・AI | 本体開発の手順と規約 |
| `Documentation/Designs/` | 本体開発者 | 機能ごとの設計判断の記録 |

**READMEとAGENTS.mdは特に混ざりやすい組み合わせです。** READMEは「使いたい人への案内」、AGENTS.mdは「エージェントへの制約」です。AGENTS.mdへAPI説明やコード例を複製せず、READMEへ開発環境の前提や内部構成を書かないでください。

## 2. 逆ピラミッド構造

**結論から書き、詳細を後ろへ置きます。** 節の順序は文書の種類ごとに固定です。並びを勝手に変えないでください。

| 文書 | 節の順序 |
| --- | --- |
| `README.md` | 概要（1〜2文） → できること（表） → まず試す → インストール → 初期設定 → 機能ごとの使い方 → Editor・デバッグ支援 → サンプル → ドキュメント索引 → 参考・ライセンス |
| モジュール文書 | 概要（1文） → 入口（表） → クイックスタート → 実装時の注意 → Editor機能 → 内部構造 → 関連 |
| ワークスペースの手順書 | 対象読者と適用範囲 → 最初に読むもの → 手順 → 確認項目 → やってはいけないこと |

- **該当しない節は省略します。順序は入れ替えません。** Editor機能だけのモジュールに「クイックスタート」を作らず、`AutoEnumGenerator.md` のように 入口 → Editor機能 → 関連 の並びを保ちます。
- 各文書の冒頭1〜2文で「これは何か」「誰向けか」を言い切る。前置きを重ねない。
- モジュール文書は1ファイルで完結させる。1つのモジュールを使うために複数の文書を読ませない。
- 内部構造は末尾に近い位置へ置く。使うだけの読み手が読み飛ばせる並びにする。

## 3. 冒頭に置かないもの

**先頭50行に次の内容が現れたら構造の誤りです。** これはAIに文書を書かせたときに最も起きやすい劣化で、直前の作業内容がそのまま冒頭へ流れ込むために発生します。

| 置かないもの | 正しい置き場所 |
| --- | --- |
| 開発環境の前提条件、Unityバージョン以外の環境設定 | ワークスペースの `AGENTS.md`。利用者向けには「対応Unity」の1行だけ |
| 内部クラス構成、レイヤー、依存グラフ | モジュール文書の `## 内部構造`、`Documentation~/Architecture.md` |
| デバッグ手順、トラブルシュート、既知の不具合 | 該当モジュール文書の `## 実装時の注意` |
| 実装経緯、検討の過程、試行錯誤の記録 | `Documentation/Designs/`、`CHANGELOG.md` |
| ビルド・コミット・検証の手順 | `Documentation/CONTRIBUTING.md` |
| 長い前置き、目的の説明の繰り返し | 削除する |

## 4. 書式

- **列挙は表にします。** 機能一覧、設定項目、対応表を段落や入れ子リストで説明しない。
- 1段落は3文以内。それを超えたら節を分けるか、表へ移す。
- 強調（`**`）は1つの節に数か所まで。全部を強調すると強調が消えます。
- コード例はクイックスタートに1つ、実装時の注意へ必要な分だけ。同じ内容を複数の文書へ複製しない。
- mermaidは内部構造の説明にだけ使い、末尾寄りに置く。HTML生成物では生成時にSVGへ変換されて図として表示されます。**図を追加・変更したときだけ、再生成に Node.js が必要です**（[CONTRIBUTING.md §6](./CONTRIBUTING.md#6-変更に応じて同時に更新するもの)）。
- 相対リンクとアンカーは実在するものだけを書く。`Documentation~/` 配下は生成時に検査され、リンク切れがあると失敗します。
- `Documentation~/` 配下で使える記法は、見出し、段落、リスト、テーブル、フェンス付きコードブロック、インラインコード、`**強調**`、リンク、水平線に限られます（[CONTRIBUTING.md §6](./CONTRIBUTING.md#6-変更に応じて同時に更新するもの)）。

## 5. 分量の目安

**常に読み込まれる文書ほど短く保ちます。** 長い指示は、指示そのものの遵守率を下げます。エージェントが毎回読む `AGENTS.md` へルールを足し続けると、既存のルールが効かなくなります。

| 文書 | 目安 |
| --- | --- |
| `AGENTS.md`（両方） | 200行未満。理想は100行程度 |
| モジュール文書 | 150行程度 |
| `README.md` | 200行程度 |
| `Documentation/` の規約類 | 上限は設けない。ただし常時読ませず、該当する節だけを参照させる |

- `AGENTS.md` が目安を超えたら、内容を該当する文書へ移し、リンクだけを残す。
- 規約類が長くなるのは許容します。代わりに、節見出しから必要な箇所だけを引けるようにしてください。

## 6. AIにドキュメントを書かせるとき

**実装セッションの続きでドキュメントを書かせないでください。** 直前まで扱っていたデバッグの詳細や設定手順が、最重要事項として冒頭へ出力されます。

1. 実装を終えたら、`/clear` などで会話の文脈を切る。
2. 変更差分（`git diff`）と、更新対象の文書だけを読ませる。実装中のログや試行錯誤を持ち込まない。
3. 指示に「どの文書の、どの節を、何行以内で」を含める。範囲を指定しないと、文書全体が書き換わります。
4. 生成後、**先頭50行を人が読みます。** §3の内容が混ざっていないかだけを見れば、劣化の大半は捕まえられます。

- **コード変更のついでにドキュメントを書き換えさせないでください。** 更新対象は [CONTRIBUTING.md §6](./CONTRIBUTING.md#6-変更に応じて同時に更新するもの) の表で決まります。表に無い文書は、明示的に指示したときだけ変更します。
- 既存のバッジ、リンク索引、手で書いた節は残します。書き直す指示でない限り、構造ごと置き換えないでください。

## 7. 更新時の確認

- [ ] 文書の種別と、書いた内容の役割が一致している（§1）。
- [ ] 節の順序が §2 の並びに従っている。
- [ ] 先頭50行に §3 の内容が無い。
- [ ] 列挙が表になっている。段落で機能を説明していない。
- [ ] `AGENTS.md` が200行未満である。
- [ ] リンクとアンカーが実在する。
- [ ] `Documentation~/` を変更したなら `python scripts/build_module_docs.py` を実行し、`Html/` の生成物を同じコミットへ含めた。
