# 監査フロー

SymphonyFramework 本体（`Assets/SymphonyFrameWork/`）を**全観点で一度に監査し、レポートだけを出す**フロー。

```text
1. 機械走査  →  2. Project Auditor  →  3. 読解と確度付け  →  4. レポート生成  →  5. 報告
```

**このスキルはコードを一切変更しない。** 指摘と修正方針を書くところまでで止める。実際の修正は
[implement スキル](../implement/SKILL.md)のフローへ、観点ごと・Round ごとに載せ替える。

**監査対象はパッケージ本体のみ。** ホスト側（`Assets/Scripts/`、`Assets/Level/` など）は対象外。
`Tests/` と `Samples/` は「テストが薄い観点」を数えるためにだけ見る。

**出力先は `Documentation/Audit/`**（ワークスペース側）。submodule の中に監査結果を置かない。
配布物に開発用の中間成果物が混ざる。

---

## 着手前: 差分の有無を確認する

`git -C "Assets/SymphonyFrameWork" status` が clean であることを確認する。

**未コミットの変更があるまま監査しない。** 指摘した `file:line` が、その後のコミットで動く。
レポートは「あるコミット時点のスナップショット」として意味を持つので、**冒頭に対象コミットの
SHA を書けない状態では始めない。**

---

## 1. 機械走査

```bash
python scripts/audit_scan.py --format markdown --out Documentation/Audit/_raw/scan.md
```

→ **[references/tooling.md](references/tooling.md)**（オプション、各分類の意味、既知の誤検出）

**この出力は場所の列挙に過ぎない。件数をそのまま指摘件数として報告しない。**
正規表現による検出なので、誤検出と取りこぼしの両方がある。ステップ3で必ず1件ずつ当たる。

## 2. Project Auditor

`uloop-execute-dynamic-code` から headless で実行し、IL レベルの指摘（ボクシング、GC Alloc、
文字列連結など）を取る。grep では原理的に取れないものがここで出る。

→ **[references/tooling.md](references/tooling.md)** の「Project Auditor」節にコード全文がある

飛ばすと事故る規則:

- **`CompilationMode.Editor` を使う。** `Player` は `AssemblyBuilder` の完了を
  `Thread.Sleep` で待つため、**メインスレッドから呼ぶと Unity ごと固まる**
- **`AssemblyNames` を指定しても依存アセンブリの指摘が混ざる。** `RelativePath` が
  `Assets/SymphonyFrameWork/` で始まるものへ必ず絞る
- **`IssueCategory.ProjectSetting` は使わない。** ホストプロジェクトの設定に対する指摘であり、
  パッケージの品質とは無関係。混ぜると指摘の大半がフレームワークと無関係な項目で埋まる
- Unity が起動していなければ `uloop-launch`。実行前に `uloop-clear-console`

## 3. 読解と確度付け

**ここが監査の本体である。** ステップ1・2の出力は候補地のリストでしかない。

観点の定義、各観点の検出手段、フレームワーク固有の判断基準は下記にある。

→ **[references/perspectives.md](references/perspectives.md)**（全観点の定義と判断基準）

各指摘へ**確度**を付ける。この3段階は `Docs/RuntimeAudit` の分類を踏襲している。

| 表記 | 意味 |
| --- | --- |
| **確定** | コードを直接読んで動作上の問題が確認できたもの |
| **要検証** | 静的に強く疑われるが、実行時の呼び出し経路次第で影響が変わるもの |
| **設計指摘** | 動作は正しいが、一貫性・保守性・拡張性の観点で改善余地があるもの |

飛ばすと事故る規則:

- **「確定」と書くなら、そのコードを実際に開いて読んでいること。** ツールの出力を
  言い換えただけのものは「要検証」より上に置かない
- **同じ問題に対する正しい実装が既にコードベース内にあるかを必ず探す。** SymphonyFramework は
  規約が行き届いているため、指摘の多くは「正しい実装と誤った実装が並存している」形を取る。
  **正しい側を見つけたらレポートに併記する。** 修正方針が「既存実装の横展開」になり、
  実装フローへ載せたときの判断が消える
- **公開APIに関わる指摘は、`Documentation/DesignPhilosophy.md` の「公開範囲」節を読んでから書く。**
  `public` を削るのは破壊的変更で、SemVer 上メジャーバージョンを要求する。**気軽に指摘しない**
- **`Documentation/CodeGuidelines.md` と `DesignPhilosophy.md` に明文の規約があるものは、
  規約の条文を引いて指摘する。** 「一般論として望ましくない」だけの指摘は採用されない
- **件数だけ書いて場所を書かない指摘を作らない。** 全件を `file:line` で列挙する（付録形式）

## 4. レポート生成

`Documentation/Audit/` へ、サマリ1本 + 観点別ドキュメントを書く。

→ **[references/report-format.md](references/report-format.md)**（ディレクトリ構成、テンプレート、付録の書き方）

飛ばすと事故る規則:

- **`00_サマリと優先度.md` に「最優先で対応すべきN件」と「費用対効果が最も高い3件」を必ず置く。**
  観点別ドキュメントだけでは、どこから手を付けるかが決まらず読まれずに終わる
- **指摘が0件の観点も節を作り、「該当なし」と書く。** 節ごと消すと、
  「見ていないのか、見て問題が無かったのか」が後から区別できない
- **良かった点も書く。** どの実装をテンプレートとして横展開すべきかが、
  修正フェーズでそのまま使える情報になる
- リンクは `Documentation/Audit/` からの相対パス。**書いたリンクは実際に辿れることを確認する**
- `_raw/` に置いたツールの生出力はコミットしない（`.gitignore` へ入れるか、レポート完成後に消す）

## 5. 報告

ユーザーへは次を伝える。

- 対象コミットの SHA、走査したファイル数・行数
- 観点ごとの「確定 / 要検証 / 設計指摘」の件数
- 最優先の指摘（**なぜ最優先なのかを1行で**）
- **ツールが見られなかった範囲**（Play Mode 実挙動、メモリリークの実測、モーダルを伴う Editor 機能）

**修正の提案までで止める。** 「直しましょうか」と聞くのはよいが、承認なくコードへ触らない。

## 監査を繰り返すときの扱い

同じ観点で2回目以降の監査を行う場合、**前回のレポートを消して書き直さない。**
前回指摘のうち何が解消され、何が残り、何が新規かを差分として書く。

指摘が2回続けて同じ場所に出るなら、それは見落としではなく**規約が明文化されていない**か、
**機械的に検出できていない**ということである。次のいずれかを提案する。

| 状況 | 提案先 |
| --- | --- |
| 規約が無いので毎回判断が割れる | `Documentation/CodeGuidelines.md` / `DesignPhilosophy.md` へ条文を追加 |
| 規約はあるが機械検出できていない | `scripts/audit_scan.py` へ検査を追加 |
| 検出はできるが毎回同じ誤検出を出す | `scripts/audit_scan.py` の除外条件を調整 |

**提案にとどめる。ドキュメントやスクリプトを勝手に書き換えない。**
