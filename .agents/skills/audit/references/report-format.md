# レポートの形式

出力先は `Documentation/Audit/`（ワークスペース側）。**submodule の中には置かない。**

```text
Documentation/Audit/
├── 00_サマリと優先度.md          ← 最初に読まれる。ここだけで着手順が決まること
├── 01_イベント購読解除漏れ.md
├── 02_Null参照リスクとガード漏れ.md
│   …観点ごとに1ファイル…
├── B1_公開APIの妥当性.md
│   …B群も観点ごとに1ファイル…
└── _raw/                          ← ツールの生出力。コミットしない
    ├── scan.md
    ├── project-auditor.json
    └── project-auditor.md
```

ファイル名は `perspectives.md` の観点番号と一致させる。**番号を振り直さない。**
2回目以降の監査で観点が増えたら末尾へ足す。

---

## 00_サマリと優先度.md

次の節を**この順で**置く。

1. **対象と条件** — 対象ディレクトリ、ファイル数、行数、監査日、**対象コミットの SHA**
2. **本監査の読み方** — 確度3段階（確定 / 要検証 / 設計指摘）の定義
3. **付録の索引** — 全件列挙を持つ付録へのリンクと件数の表
4. **観点別ドキュメントの索引** — 観点ごとの「確定 / 要検証 / 設計」件数の表
5. **最優先で対応すべきN件** — 影響度 × 確度 で並べた表。`file:line` と観点番号を必ず付ける
6. **費用対効果が最も高い3件** — **修正が数行で済むのに影響が広いもの**
7. **全体所感** — 強みと、指摘の性質（破綻の修復か、水準を揃えるものか）

### 「最優先で対応すべきN件」の書き方

| 順 | 内容 | 場所 | 観点 |
| --- | --- | --- | --- |
| 1 | （何が起きるかを1行で。「〜が漏れている」ではなく「〜のため〜が起きる」） | [File.cs:123](../../Assets/SymphonyFrameWork/...) | 03 / 11 |

- **「何が悪いか」ではなく「何が起きるか」を書く。** 着手順はリスクで決まる
- 観点をまたぐものは観点番号を複数書く
- **N は固定しない。** 該当が3件なら3件でよい。数合わせで薄い指摘を混ぜない

## 観点別ドキュメント

```markdown
# 01. イベント購読解除漏れ

（何をどう突き合わせたかを1〜2行。再現できる形で書く）

## 調査サマリ

| 分類 | ファイル数 |
| --- | --- |
| 購読(`+=`)があり解除(`-=`)が一切ない | 0 |
| `+=` が `-=` より多い | 0 |

---

## 【確定・最優先】（見出しは指摘の内容そのもの。「問題1」のような番号にしない）

**場所**: [File.cs:258-274](../../Assets/SymphonyFrameWork/...)

（該当コードの引用。省略した部分は `// ...` で示す）

（なぜ問題なのか。**何が起きるかを具体的に。** 「リークする」ではなく
「シーンを往復するたびに購読が積み上がり、次の発火で MissingReferenceException になる」）

**修正方針**: （方針を1行 + 修正後のコード）

（**同じ問題に対する正しい実装がコードベース内にあるなら必ず併記する。**
「なお同じ EventBus を使う X と Y は正しく解除されている。このファイルだけが例外」）

---

## 付録A: （機械的に列挙したもの）（全N件）

| 場所 | 内容 |
| --- | --- |
| `Assets/SymphonyFrameWork/...:12` | ... |
```

### 規則

- **見出しに確度を含める** — `【確定】` `【要検証】` `【設計指摘】`
- **指摘が0件の観点もファイルを作り、「該当なし」と書く。** 節ごと消すと
  「見ていないのか、見て問題が無かったのか」が後から区別できない
- **件数だけ書いて場所を書かない指摘を作らない。** 全件を `file:line` で列挙した付録を末尾に置く。
  `audit_scan.py --format markdown --category <name>` の出力をそのまま貼れる形になっている
- **リンクは `Documentation/Audit/` からの相対パス**（`../../Assets/SymphonyFrameWork/...`）。
  書いたリンクは実際に辿れることを確認する
- **公開APIに関わる指摘には、破壊的変更になるかどうかを必ず書く**

---

## 書いてはいけないもの

- **修正済みのコード。** このスキルはレポートまで。`修正方針` に断片を示すのはよいが、
  ファイルへ書き込まない
- **ツールの出力の言い換えだけの指摘。** 「Project Auditor が boxing を報告している」だけでは、
  それがホットパスなのか初期化1回なのかが分からず、着手判断に使えない
- **一般論だけの指摘。** `Documentation/CodeGuidelines.md` / `DesignPhilosophy.md` に
  明文の規約があるものは条文を引く。無いものは「規約が無いので判断が割れる」と書き、
  規約追加の提案としてサマリへ回す
- **数合わせの指摘。** 観点あたりの件数を揃えようとしない
