# 実装フロー

SymphonyFramework 本体（`Assets/SymphonyFrameWork/`）へ機能を追加・変更するときの標準フロー。

```text
1. 設計書を書く  →  2. ワーカーが実装する  →  3. 実装を確認する  →  4. バージョンを更新する  →  5. コミット・PR  →  6. 振り返る  →  7. 設計書へ実施レポートを書く
```

各ステップは前のステップの完了を前提にする。**ステップを飛ばさない。** 特に 1 を飛ばしてワーカーに実装させないこと。設計判断が残らず、レビューの基準も失われる。

## 全 Round 共通: テストの実装は必須

**本体のソース（`Runtime/` `Core/` `Editor/`）を変更する Round は、同じ Round でテストを追加または変更する。** ステップ2の成果物にテストを含め、ステップ3で件数の増加を実測する。

**`release_round.py preflight` が機械的に検査する。** ソースの `.cs` を変更していて `Tests/` の変更が無い Round は、preflight で止まる。

**検証手段が無い場合だけ、理由を明示して通す。**

```bash
python scripts/release_round.py commit --message "[fix]説明" --no-tests-reason "EditorWindowのGUI操作は自動検証できないため"
```

理由は `No-Tests-Reason:` トレーラとしてコミットへ残る。**通した事実が履歴に残らない抜け道を作らないための形である。** 使ってよいのは次のような場合に限る。

| 理由 | 例 |
| --- | --- |
| Editor の GUI 操作を伴う | EditorWindow のボタン・トグルの押下（→ ステップ1の「アクセス手段の検証」） |
| Unity のホストライフサイクルに依存する | Domain Reload、Editor の起動・終了、モーダルダイアログ |
| ソースを変更していない | ドキュメントのみ、`package.json` のみ |

**「テストが書きにくい」は理由にならない。** 書きにくい形になっていること自体が設計の指摘であり、ステップ1でロジックを Unity API へ触れない型へ切り出す判断をする。実際に、Issue #161 の対象は `async void` とファイルI/Oの中にあって単体で検証できなかったため、判定だけを `internal static` の純粋関数へ切り出してテスト可能にしている。

ホスト側（`Assets/Scripts/` など、パッケージを利用するだけのコード）の変更にはこのフローを使わない。通常どおり直接実装する。

**詳細は各ステップの参照先にある。着手するステップの参照先を読んでから進めること。**

---

## 着手前: タスクの大きさとブランチ

1回のフローで扱えない大きさなら、着手前に **Round** へ分割する。Issue 対応なら専用ブランチを切る。

→ **[references/rounds.md](references/rounds.md)**

Round の目安は「単独で検証でき、単独でリリースできる」単位で、**差分を自分で全部読める規模（おおむね20ファイル以内）**。前の Round がコミットまで終わってから次へ進む。

---

## 1. 設計書を書く

`Documentation/Designs/<機能名>.md` を作成し、**実装へ進む前にユーザーへ提示して合意を取る。**

→ **[references/design-doc.md](references/design-doc.md)**（テンプレート、アクセス手段の検証）

飛ばすと事故る規則:

- **「この経路で届く」と書いたら、書いた時点でコードを見て確かめる。** 可視性（`private` / `internal` / `public`）とアセンブリ境界を実際に確認する
- **既存コードに回避策（リフレクション、`#if`、コピー実装）がある場合は、それが存在する理由を説明できるまで設計を確定しない**
- **「各サブシステムの X を〜する」のような横断的前提は、全対象に存在し必要な可視性を持つことを列挙して確認する。** 一部にあることは全部にあることの証拠にならない
- テストは**何を検証するかだけでなく、どう書くかを1行で書く**。書けない要件に気づけない

## 2. ワーカーが実装する

`scripts/codex_runner.py` 経由で Codex CLI ワーカーへ委譲する。`codex` を直接呼ばない。

→ **[references/worker.md](references/worker.md)**（呼び出し方、プロンプトのテンプレート、終了コードの扱い）

飛ばすと事故る規則:

- **プロンプトへ「前提が崩れたときの扱い」ブロックを毎回そのまま含める。** ワーカーが黙って回避策へ切り替えると、その Round の目的自体が失われる
- **ワーカーが報告するコンパイル結果やテスト件数は環境差を含む。必ずステップ3で自分で再実行して確認する**
- **長時間応答しない場合は打ち切って自分で引き継ぐ。** 実質的な出力が止まってから30分を目安にする
- **残量不足（`exit 2`）やワーカーが使えないときは、リセットまでの時間を見て待つか自分で実装するか決める。** 日単位で回復しないなら自分で実装する。その場合も設計書・検証・振り返りは省略せず、**独立した目が入らない分を契約項目の照合とテストで補う**

## 3. 実装を確認する

**ワーカーの報告を鵜呑みにしない。必ず差分を自分で読む。**

Unity 側の検証は**スクリプトで一括実行する。`uloop` を1つずつ手で叩かない。**

```bash
python scripts/verify_round.py
```

clear-console → compile（確定後の値を採用）→ Console 確認 → EditMode → PlayMode 2往復 → Enter Play Mode Options の検査を1プロセスで行い、結果を1つの要約で返す。**Domain Reload 中の待ち直しと、確定前の値を捨てる処理を内部で持つ**ため、手で叩いたときの往復（今回のラウンドで10回以上）が1回になる。

→ **[references/review.md](references/review.md)**（レビュー観点、機械的検索、Unity Scene の検証ガード）

飛ばすと事故る規則:

- 目視だけに頼らず、**機械的に検索できる違反は検索する**（Runtime/Core からの `UnityEditor` 参照、テスト用 asmdef の `UNITY_INCLUDE_TESTS`）
- コンパイルは**エラー0・警告0**。テストは全数成功
- Domain Reload 無効のため、**Play Mode の開始・終了を2回繰り返してゴースト参照が残らないことを確認する**
- 新規ファイルの `.meta` が `.cs` と対で揃っていること（`release_round.py preflight` が見る）
- **Editor の画面を変えたなら、開いて見る。** 押下は自動化できないが、スクリーンショットと表示要素の実値の読み取りはできる。**コンパイルとテストが全数通っていても、レイアウト崩れと表示文言の誤りはここでしか見つからない**
- **差し戻しや自分で直す際も、代替手段が成立することを実測してから採用する**

## 4. バージョンを更新する / 5. コミット・PR

`package.json` の `version` と `CHANGELOG.md` の見出しを**同時に**更新し、submodule → 親リポジトリの順でコミットする。

**git は手で叩かず `scripts/release_round.py` を使う**（`preflight` / `commit` / `finalize`）。順序と検証がコード化してある。

→ **[references/release.md](references/release.md)**（スクリプトの使い方、CHANGELOG の書き方、2段階コミットとPRの手順）

飛ばすと事故る規則:

- **ステップ3の検証が1つでも失敗しているならコミットしない**
- **submodule を push しないまま親の gitlink を更新しない**
- **親の gitlink は `develop` に到達可能なコミットを指すこと。** PR マージ前の feature ブランチのコミットを指すと、squash マージやブランチ削除で到達不能になる
- **親リポジトリも push する**
- 無関係な既存の未コミット変更は別コミットへ分ける。判断がつかないものは残して報告する
- 何をコミットし、何を意図的に残したかを必ず報告する

---

## 6. 振り返る

ラウンドを閉じる前に、**そのラウンドで起きた手戻りを振り返り、仕組みへ還元できるものをユーザーへ提案する**。ここを飛ばすと、同じ種類の欠陥を毎回レビューで拾い直すことになる。

見る対象:

- **ワーカーへ差し戻した内容** — 何を指示し忘れたのか。プロンプトか設計書のテンプレートに項目が足りていなかった可能性がある
- **レビューで見つけた欠陥の傾向** — 同じ種類が2回以上出たら、それは個別の見落としではなく仕組みの穴
- **設計書と実装が食い違った箇所** — 設計書の記述が曖昧だったのか、実装が逸脱したのか
- **手順の途中で判断に迷った点** — ドキュメントに書かれていない暗黙の前提がある
- **繰り返した定型動作** — **同じ手順を2回以上手で叩いたなら、スクリプト化できないかを検討する。** 下記を参照

### 繰り返した定型動作はスクリプト化を検討する

**ラウンド中に同じ git 操作・同じ確認・同じ後始末を2回以上手で叩いていたら、それは手順書ではなくコードで固定すべき候補である。** 手順書に書いても、書いてあることと実行されることは別で、抜けても誰も気づかない。

判断の目安:

| 状況 | 扱い |
| --- | --- |
| 順序を間違えると壊れる、抜けると後で困る | **スクリプト化する。** `scripts/release_round.py` へフェーズか処理を足す |
| 毎回同じだが、抜けてもその場で分かる | 手順書に書く。スクリプト化は任意 |
| 毎回内容が変わる、判断が要る | スクリプト化しない。判断を奪うだけになる |

実例: マージ後の後始末（`develop` への復帰、fast-forward、ローカル `feature/*` の削除）を毎ラウンド手で叩いていた。`gh pr merge --delete-branch` はリモートのブランチしか消さないことがあり、抜けても当面は困らないため気づきにくい。`release_round.py finalize` へ取り込んで解消した。

**既存スクリプトへ足せないかを先に見る。** 新しいスクリプトを増やすと、どれを呼ぶかの判断が増える。

提案する先:

| 気づき | 提案先 |
| --- | --- |
| 繰り返す定型動作で、順序や抜けが事故になるもの | `scripts/release_round.py` などのスクリプト |
| 繰り返す手作業、毎回同じ確認 | 新しいスキル、またはこのスキルへの手順追加 |
| コードの書き方・配置・命名の抜け | `Documentation/CodeGuidelines.md` |
| レイヤー、依存方向、公開範囲の判断が割れた | `Documentation/DesignPhilosophy.md` |
| 作業手順、コミット、バージョン、検証の抜け | `Documentation/CONTRIBUTING.md` |
| 設計書に書くべき項目の不足 | このスキルのステップ1のテンプレート |

**提案にとどめる。ドキュメントやスキルを勝手に書き換えない。** 何をどう変えるかまで具体的に示し、ユーザーの承認を得てから反映する。

気づきが無ければ「無し」と述べて閉じる。無理に挙げる必要はない。

## 7. 設計書へ実施レポートを書く

**ラウンドを閉じる最後に、`Documentation/Designs/<機能名>.md` の末尾へ `## 実施レポート` を追記する。**

設計書は着手前に書くため、**そのままでは「やるつもりだったこと」しか残らない。** 実際に何を作り、何が設計と食い違い、何を確認できて何を確認できなかったのかは、会話の中だけに残って消える。次に同じ場所を触る人（自分を含む）が読むのは設計書であって、会話ログではない。

チャットへ書いた報告と同じ内容を、設計書へも残す。**チャットだけで報告して終わらせない。**

```markdown
## 実施レポート

実施日: YYYY-MM-DD / バージョン: x.y.z / PR: #<番号>

### 実装した内容
設計のどこを、どのファイルで実現したか。設計書の前半と対応が付く粒度で書く。

### 設計から変えた点
着手後に変えた判断と、その理由。**変えていないなら「無し」と書く。**
ここが空欄のまま埋め忘れられやすいので、無しならそう書く。

### 検証結果
`verify_round.py` と `release_round.py preflight` の実測値。件数まで書く。
**ワーカーの報告ではなく、自分で再実行した値を書く。**

### 未実施の確認
自動で検証できず、人の操作が要る項目。**「動作確認手順」のどの項目が未実施かを明示する。**
残っていることを書かないと、確認済みだと誤解される。

### 振り返り
ステップ6で挙げた気づきと、適用したもの・見送ったものの区別。
```

**実施レポートは設計書の末尾へ追記する。設計の記述を書き換えない。** 着手前の判断と実施後の事実が分かれて残ることに意味がある。設計が間違っていた場合も、設計を直すのではなく「設計から変えた点」へ理由付きで書く。
